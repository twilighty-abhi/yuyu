## [Unreleased] — production release 2026-10-27

The first production deploy since the 1.0.0 release (production `bf7a04d`, 2026-10-21): the latest `main` (after the release-gate fixes in #27 and #29), about 125 commits and 13 migrations. ### Added

- **Event crew**, specified in `docs/CREW.md`. Organisers keep an event's organising team in **Guests → Crew** (name, email, food preference with a grouped summary, role, bio, photo, LinkedIn; add, edit, reorder, show or hide, remove), with `MANAGE_REGISTRATIONS`. Each member gets a confirmed crew ticket by email ("You're on the crew for …") that checks in like any other and shows a **Crew** chip, but never counts against `Event.capacity`; adding someone who registered solo converts that registration (same ticket, place freed), and team members are refused. Crew tickets cannot be self-cancelled or edited and removed from Guests · People, and never join teams. A crew sign-up link (`/crew/:token`; create, rotate, disable) adds members hidden until reviewed, refuses cancelled and ended events, and answers duplicates and existing registrations like a new sign-up. An optional **Crew** section on the event page (off by default) shows visible members' cards. New audit actions `EVENT_CREW_*`. Cores in `lib/core/crew.ts`, actions in `app/actions/crew.ts`. Unit suite `tests/unit/crew.test.ts`, PostgreSQL suite `tests/integration/crew.db.test.ts`.
- Migration `20261029000000_event_crew` (additive: `RSVP.isCrew` defaulting to false, the `EventCrewMember` and `EventCrewJoinLink` tables, the `CREW` page section type, and the `RSVP_crew_shape` CHECK constraint, added `NOT VALID` and then validated).
- **Attendance confirmation ("Are you still coming?").** From a new **Attendance confirmation** card on the event Emails tab, organisation owners and admins (the same rule as custom emails) can ask every confirmed guest of a one-off event, one email each, whether they are still coming. Nothing is sent automatically: each send follows a preview (the number of guests, the event date, and a note about the sending limit) and an explicit confirmation. A repeat send asks only guests confirmed since (**Ask newly confirmed guests**), and **Remind people who haven't replied** emails non-repliers again at most once every 12 hours, each time with a new link. Guests answer Yes or No, with an optional note, on a private form at `/attend/:token` (emailed buttons preselect the answer) and can change their answer until the event starts. An optional **Free the place when a guest says No** switch (off by default) cancels the registration through the normal self-cancel path, so the waitlist and team rules apply. Guests → People gains a per-guest badge, the note, and a server-side **Attendance confirmation** filter with counts (kept in saved views as `attendance=`). The attendee CSV gains **Attendance confirmation** and **Attendance note** columns, the check-in desk shows the badge, the Overview readiness card shows a counts-only replies line to owners and admins, and the personal data export includes your own answers. The email only says that a No gives up the place when the switch is on. Cloning an event copies the switch but not the answers. New outbox kind `attendance-check` (a capability, deleted after delivery, expires at the event start), audit actions `ATTENDANCE_CHECK_SENT`, `ATTENDANCE_CHECK_REMINDED`, `ATTENDANCE_CHECK_SETTINGS_UPDATED` and `ATTENDANCE_CHECK_RELEASED`, and rate-limit buckets `attendanceCheckSend` (10 per hour), `attendanceCheckSettings` and `attendanceCheckReply`. Core in `lib/core/attendanceCheck.ts`, Server Actions in `app/actions/attendance-check.ts`. Series occurrences and the mobile API are not covered yet (`docs/FUTURE_PHASES.md`).

### Changed

### Security

- Attendance confirmation links (`/attend/:token`) are 256-bit bearer capabilities, stored only as a SHA-256 hash and rotated by reminders. The page shows only the guest's own name, email and answer (never other attendees, the ticket or check-in token), is `noindex`, `no-referrer` and `private, no-store`, is disallowed in `robots.txt`, and answers a real 404 for an unknown, replaced or released link. Replies are rate limited per link and per address.
- Submission links are random 256-bit tokens stored only as SHA-256 hashes, emailed only to the registration's own address (at most once a minute), and retired when replaced; the outbox deletes the message after delivery. The ticket QR alone never opens a submission.
- `JUDGE` never satisfies any other event permission check. Judges see project content only, never entrant emails, answers, or tickets, and never an entry their own account is registered on. Disqualification reasons and judge comments stay organiser-only; scores and comments are never public.
- Entrant, judge, and organiser ids are re-read with their event and organisation inside each write transaction, and the submission window is compared with server time there.
- **Dependency advisories patched.** `next` 16.3.8 → 16.4.2 (GHSA-2464-fhr4-w9xw, GHSA-673q-mjm6-r5xr, GHSA-p3m5-59mp-jv5r) with `eslint-config-next` in step, `zod` 4.3.6 → 4.6.7 (GHSA-mrhx-c7xc-m3w5) and `nodemailer` 10.0.10 → 10.2.1 (addressparser GHSA-8c8m-p3m8-cjg8, GHSA-m943-m63m-w62w, GHSA-85x2-q946-cp5h). No application code changes; `npm audit --omit=dev` reports 0 vulnerabilities.
- **Signed-in and capability-link pages are never cached.** The proxy marked only ticket, team and submission pages `private, no-store`; every other page got a bare `no-transform`. Dashboard, account and super-admin pages, `/login`, `/join/*` invitations, `/reset-password` and `/verify-email` now send `private, no-cache, no-store`, as does any request carrying the session cookie. The invitation, reset and verification links also send `Referrer-Policy: no-referrer`, and the reset page gains `noindex` and `no-referrer` meta tags.
- Ticket, team, team-join and submission pages send `private, no-store` in production, alongside the attendance confirmation and crew sign-up pages; all of them are `noindex` and `no-referrer`, and `robots.txt` disallows them.
- Organisation webhook targets are SSRF-restricted at save and delivery time (public `https` on 443/8443, every resolved address checked, pinned connection, no redirects). `WEBHOOKS_ALLOW_PRIVATE_TARGETS` is for development and CI tests only: production ignores it unless both `CI=true` and `ALLOW_INSECURE_PRODUCTION_TESTS=1` are set, and `npm run production:check` refuses it outside that mode. Remove it from any production environment.
- Help-centre sections for owners and admins and for the super-admin are checked on the server for every page, metadata and search-index request, and answer a real 404 to anyone else.
- **The rate limiter answers at once while Redis is down.** ioredis queued each command behind its reconnect backoff, so requests stalled for 1 to 30 seconds (readiness beyond the Helm probe timeout) before failing closed. Commands now have a 500 ms deadline, and while ioredis is reconnecting the limiter answers immediately (`lib/redisOptions.ts`, shared with realtime check-in).

### Fixed

- **Large-event dashboard memory.** Opening the event dashboard of a 15,000-registration event built about 62,000 `Intl.DateTimeFormat` objects (one per registration date in the Analytics panel), allocating over a gigabyte of native memory that Node kept, and took 2–8 s. Formatters are now cached (`lib/format/intlCache.ts`) and reused by the date helpers, the Analytics metrics and time-zone validation: one open takes about 0.3 s, and 20 concurrent opens peak at about 1.4 GB instead of about 5 GB. Public pages build far fewer formatters too. Unit suite `tests/unit/intl-formatter-cache.test.ts`.
- **Outbox throughput and priority.** Each scheduler pass now drains the email queue in batches of 50 for up to 40 seconds instead of 20 messages a minute, and stops early when a whole batch fails. Transactional email is claimed before bulk sends (`event-broadcast`, `attendance-check`, `results-published`, `event-invite`), so a large attendance confirmation no longer delays password resets and tickets for hours. New email kinds that an older release failed as unknown during a rolling update are requeued once.
- **Raw SQL on a non-UTC database.** The attendance reminder, the webhook delivery claim, judge score and review upserts and the discover page's date filters passed JS dates and `now()` to PostgreSQL as `timestamptz`, which the server converted with its session TimeZone, so on a non-UTC database reminder times were stored hours off and webhook retries fired early or late. - **New events' public pages show their sections.** An event created from the New event dialog has no saved section rows, and its public page showed no About, Venue, Programme or Speakers while Event page → Sections listed them as on. The public page now applies the dashboard's rule (sections without a saved row are on, except Crew).

- Two organisers publishing the same draft at once now emit one `event.published` webhook and write one `EVENT_PUBLISHED` audit row.
- A webhook endpoint's queued deliveries keep their own last error when the endpoint is switched off automatically.
- `robots.txt` names the sitemap with an absolute URL.
- Judging → Progress no longer scrolls sideways at phone width (tables now contain their screen-reader-only text).
- The Create Event dialog's default start is at least 30 minutes away, focus returns to **New event** after closing the dialog, and moves into each step after **Next** or **Back**.
- Seeker **Invite** buttons and the check-in desk's **Undo** buttons name the person they act on.
- A full event's registration dialog says it is the waitlist; the co-organiser invitation uses British spelling; feedback from an unregistered address on an event with certificates explains what to change.

- Auth.js / NextAuth v5: Google OAuth (optional via env) and email magic link with **stub** `sendVerificationRequest` (logs link to server console)
- Domain models: `User`, `Organisation`, `Membership` (OWNER / ADMIN / MEMBER), `Event` (DRAFT / PUBLISHED), `RSVP` (logged-in or guest email) with `attendeeKey` for deduplication
- Organisation creation with creator as OWNER (transaction)
- Event creation with title-based slug and collision suffix; members can create; only OWNER/ADMIN can publish or create as PUBLISHED
- Public org page `/{orgSlug}` and public event page `/{orgSlug}/{eventSlug}` (published events; draft events visible to org members only)
- RSVP server action with capacity check and duplicate handling
- Material UI v9 theme (MD3-inspired tokens), responsive layout, event cards, dialogs, RSVP form
- Zod validation for org, event, and RSVP payloads
- SEO: `generateMetadata` on published event pages
- Documentation: `docs/FUTURE_PHASES.md` for deferred scope and later phases

### Security

- Dashboard routes require session
- Event creation requires organisation membership
- Publishing requires OWNER or ADMIN
- Public RSVP only for PUBLISHED events

### Not in scope (Phase 1)

- Recurring events, waitlists, invite-only flows, approval workflows
- Transactional email delivery (beyond development stub)
- Analytics, ticketing, payments
