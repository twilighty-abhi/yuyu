# Features

[Documentation index](README.md)

## Accounts and authentication

- Email/password signup and sign-in with bcrypt password hashing and one-time inbox verification before account activation.
- Account area with Profile (name, photo, email status, Light/Dark/System appearance), Registrations (your upcoming and past tickets with cancel, certificates, and a personal JSON data export that never includes passwords, security codes or ticket links), Organisations (memberships and roles, event co-organiser roles, pending co-organiser invites, and leaving an organisation, blocked for the only owner), and Security (password, two-step verification, sign-in methods, recent security activity, sign out everywhere).
- Optional Google OAuth.
- Password-reset requests delivered through the transactional outbox.
- Authenticator-app MFA for credential accounts, including recovery codes.
- Account pages at `/account`, `/account/registrations`, `/account/organisations`, and `/account/security`. The personal data export (`GET /api/exports/account`) returns only the signed-in user's own allow-listed data as JSON, is limited to five downloads per hour, and is audited as `ACCOUNT_DATA_EXPORTED`. Leaving an organisation removes only your own membership, is refused for the sole owner, and is audited as `ORGANISATION_MEMBER_LEFT`.
- JWT session-version invalidation after sensitive account operations.
- A user-authenticated mobile API (`/api/mobile/v1`) for the Yuyu mobile apps (Android and iOS): email/password and Google sign-in with rotating refresh tokens, your registrations and tickets, public discovery and registration, organiser day-of work (guest and whole-team approval, check-in with offline roster and sync, attendee emails, the programme with speakers and live delays, feedback open/close, closing sign-ups), and a judge's scoring workspace. Mobile sessions end with "sign out everywhere" and password or MFA changes. Android App Links and iOS Universal Links association files are served under `/.well-known/` when configured. See [Mobile API](MOBILE_API.md).

Google OAuth users rely on the Google account's MFA policy; the application TOTP prompt applies to password authentication.

## Help centre

- An in-app guide at `/help` for guests, organisers, door staff, developers and the instance administrator: 68 articles in 14 sections, from getting started and registering to judging, check-in and troubleshooting, with screenshots and an "On this page" outline. It replaces the PDF user manual.
- Search across every article the viewer may read, jumping to the matching section.
- Dashboard screens have **Help** links to the matching article.
- Most sections are public. *Connecting other tools* (machine API and webhooks) is shown only to owners and admins of any organisation, and *Instance administration* only to the super-admin; for anyone else those pages are a real 404, and the search index leaves them out.
- Articles are MDX files in `content/help/`, listed in `content/help/manifest.ts`; `content/help/README.md` is the writing and screenshot guide.

## Organisations and permissions

- Multiple organisations per user.
- `OWNER`, `ADMIN`, and `MEMBER` roles.
- Organisation profile, slug, description, and logo management.
- Member role changes and removals with owner-protection rules.
- Expiring, revocable organisation invitation links.
- Organisation deletion (the owner types the organisation's exact name to confirm) and audited administrative changes.
- Outgoing webhooks (owners and admins, **Settings → Webhooks**): up to 10 signed endpoints per organisation for registrations, status changes, check-ins, publish/cancel and feedback, with a reveal-once signing secret, rotation, test sends, a delivery log with redelivery, automatic retries and auto-disable. Payloads carry names and statuses only. See [Organisation webhooks](WEBHOOKS.md).
- Event collaborators (co-organisers) invited per event through expiring links (`/join/event-collaborator/:token`), with exact grants: `EDIT_DETAILS`, `MANAGE_REGISTRATIONS`, `MANAGE_INVITATIONS`, `CHECK_IN`, `PUBLISH_AND_SCHEDULE`, and `JUDGE`. Collaborators reach only the events they were granted. `EDIT_DETAILS` covers event-page content (page settings, highlights, speakers, sponsors, resources, FAQs) and setting up custom check-in lists, `MANAGE_REGISTRATIONS` the guest list (approvals, waitlist, manual guests, edits, removals, attendee CSV, registration numbers), `MANAGE_INVITATIONS` the invite list, `CHECK_IN` the check-in desk, badges and scanning into custom check-in lists, `PUBLISH_AND_SCHEDULE` the programme schedule, and `JUDGE` the hackathon judging workspace only (scoring assigned entries; never available on a series, and never any other control); the other grants apply the same way on a series page. Setting the event Live, short links, the Details form, the registration form, emails, feedback, reports, the check-in station PIN, cloning, embedding, deleting, co-organisers, judging settings, and organisation settings stay with owners and admins (see [Permissions](PERMISSIONS.md)).

## Events

- Draft, published, hidden, and cancelled event states; the dashboard labels the first three Draft, Live, and Offline.
- A three-step **Create Event** dialog (Basics, Schedule, Location & platform) creates a draft and opens its event dashboard (`components/event/CreateEventDialog.tsx`).
- The event dashboard has eight tabs: Overview, Guests, Event page, Emails, Check-in, Feedback, Analytics, and Settings. Old `?tab=details|registration|invites` links still open the right place.
- A single event publication state controls both public website visibility and RSVP availability. Publishing sets `Event.status = PUBLISHED` and releases the event page (`EventPage.isPublished = true`) together, whether it is done in the Publishing section or with **Publish event** on the Overview readiness checklist (`publishEvent` in `app/actions/event.ts` writes both in one transaction and creates the page row if a cloned or older draft has none). Saving the event page for an event that has no page row yet creates it released exactly when the event is published. A Live event's public page, sign-ups, and short link therefore work immediately.
- The event's **Publishing** section asks three questions: who can see it (Draft, Live, Offline), who can find it (everyone, people with the link, or invited people, plus an *Approve each sign-up* switch), and sign-ups (spots, a single close-sign-ups rule, and whether to show the count), with a live summary line.
- Title, description, tags, timezone, dates, location, online status, capacity, and cover image.
- Cover photo editor: 16:7 event banner by default (16:9 and square also available), drag/pinch/wheel/keyboard positioning that always covers the frame, rotate, straighten, flip, brightness/contrast/saturation and preset looks, guides, and card/social-share previews. The edited image is exported as WebP (JPEG fallback) and still passes the normal server-side upload pipeline.
- Event page accent colour from presets or a custom picker (saturation/brightness area, hue slider, hex input, the system eyedropper where supported, and a live contrast-checked sample).
- Public, hidden-link, approval-required, and invite-only privacy modes; approval-required events can also be listed publicly (organisation page, Discover, search) through `Event.listedPublicly`. Every listing uses the shared `listedEventAudienceWhere` rule, and sign-up approval still applies.
- Optional display of confirmed registration counts.
- Parallel programme tracks for rooms, stages, and streams; live delays cascade only within the affected track, while same-track time overlaps remain visible as organiser warnings.
- Event cloning, publishing, slug changes, and deletion.
- Optional event short links (`/aB3x9Kq`): organisation owners and admins create one on demand from the event dashboard and can regenerate it, which retires the old code. The link follows slug changes, and the event page still applies its own privacy and invite rules.
- An embeddable event card at `/embed/:orgSlug/:eventSlug`, with in-frame registration, framable only by the origins in `ALLOWED_EMBED_ORIGINS`.
- Verified email ownership is required before creating events, recurring series, clones, or event cover images.
- Private event and series email allowlists.
- Cover images are decoded, resized, metadata-stripped, and re-encoded to WebP before storage.

## Registration and RSVP lifecycle

- Guest registration by name/email and registration for signed-in users.
- Custom registration questions: text, textarea, email, phone, select, multiselect, radio, checkbox, number, and date.
- Per-question help text, placeholders, and settings: length, number and date limits, maximum selections, an "Other" answer, and "show only if" logic based on an earlier choice or yes/no question. Question keys are generated from the question text and never shown. The server enforces every setting and drops answers to questions hidden by logic.
- Required-field and option validation on the server.
- Duplicate RSVP prevention per event or instance.
- Capacity-aware confirmation and waitlisting.
- Pending approval, approval, rejection, cancellation, and waitlist promotion.
- Re-accepting a declined registration (**Re-accept** on a declined guest in the Guests list, or `POST …/guests/:rsvpId/reaccept` in the mobile API): organisation admins can reverse a decline while the event or occurrence is still open. It takes the same locked capacity check as an approval: the guest is confirmed when there is room and otherwise moved to the waitlist (never oversold), gets the approval or waitlist email through the outbox, and the change is audited as `RSVP_REACCEPTED`.
- Removing an RSVP creates a short-lived, server-owned undo snapshot.
- Confirmation and lifecycle emails are queued through a durable outbox.
- Confirmed RSVP emails include an `.ics` calendar invitation with the event or occurrence time and location.
- Event dashboard invitations are queued through the same durable outbox and link invitees to the event registration page.
- Organisation admins can email selected groups of existing registrations from the event's **Emails** tab: choose any combination of confirmed, waitlisted, pending-approval, and rejected registrations, optionally narrowed to people who did or did not check in. Thirteen starter templates (reminders, know-before-you-go logistics, agenda updates, speaker announcements, schedule or venue changes, cancellation, waitlist and approval updates, on-the-day notes, thank-you, missed-you, and slides/resources) prefill the subject, a rich-text message, and a suggested audience. The editor supports headings, bold/italic, lists, quotes, links, call-to-action buttons, and placeholders for `{{name}}`, `{{event}}`, `{{eventDate}}`, `{{location}}`, `{{eventUrl}}`, `{{ticketLink}}`, `{{feedbackUrl}}`, `{{scheduleUrl}}`, and `{{organisation}}`. Message HTML is reduced to a small sanitised subset on the server, a plain-text alternative is generated automatically, and the dashboard preview is rendered by the server with the real email template at desktop and mobile widths. Five visual designs (Classic, Minimal, Accent band in the event colour, Photo header with the event cover, and Letter) frame the same content; the choice is stored with each broadcast and used for the preview, tests and delivery. Organisers can send themselves a test, review the recipient count and subject in a confirmation step that must be ticked before sending, undo within five seconds, and reuse any previously sent email with its design. Each recipient is a separate outbox message rendered at delivery time, one per email address; ticket links are only inserted for confirmed registrations, and a registration that leaves the audience before delivery is skipped. Sends are rate limited and audited without recipient data. Test sends link `{{ticketLink}}` to the organiser's own ticket when they are confirmed for the event, and otherwise to the event page. Sent emails build image and site links from `NEXT_PUBLIC_BASE_URL`; without it, the photo header falls back to the colour band and site-relative images are left out (the dashboard preview works either way).
- Custom emails in the **Emails** tab are kept as a draft on the server, one per organiser and event, so they survive a reload, another device, or a closed tab. The draft (subject, sanitised message, design, audience, and the template it started from) autosaves about 1.5 seconds after typing stops, with a **Save draft** button for unsaved changes and a quiet status line ("Unsaved changes", "Saving…", "Draft saved · 2:41 PM", or "Couldn't save · Retry"). Opening the tab restores it. Loading a template or reusing a sent email asks before replacing a draft, **Discard draft…** asks before removing it, and the browser warns before closing the page with unsaved changes. Drafts are private to their author (teammates never see them), need the same owner/admin access as sending, and are removed when that organiser sends the email from the dashboard, after the five-second undo window; test sends keep the draft. Drafts are deleted with their event or their author's account. The mobile API does not use drafts yet.

### Attendance confirmation ("Are you still coming?")

A final check before the event, sent by hand from the event's **Emails** tab (the **Attendance confirmation** card). Nothing is ever sent automatically: there is no schedule or timer, and the outbox worker never creates a question. Most organisers send it 1–2 days before the event, but it is always their decision.

- **Who can send:** exactly the people who can send custom emails, organisation owners and admins (the same `canManageEvents` rule as broadcasts). No co-organiser grant covers emailing guests, so collaborators of every grant (including `JUDGE`) are refused, and the card is not shown to them.
- **Who is asked:** every CONFIRMED registration of the one-off event, one email per person (each team member individually), to the registration's own address. Waitlisted, pending-approval, rejected and cancelled registrations are never asked. Recurring-series dates are not covered (see `docs/FUTURE_PHASES.md`).
- **Sending:** **Ask guests to confirm attendance** first shows a preview (how many confirmed guests will be asked, the event date, and a note that each guest gets one email and that every email counts towards the sending limit) and sends only after an explicit confirmation. Each send creates one `AttendanceCheck` per registration and queues one outbox email. Anyone already asked is skipped (the unique `rsvpId` plus a row lock on the event), so a double click or two organisers at once never ask anyone twice. Later, the same button reads **Ask newly confirmed guests** and asks only people confirmed since (for example, promoted from the waitlist). Sending is refused once the event has started and for a cancelled event.
- **Reminders:** **Remind people who haven't replied** emails confirmed guests without a reply again, at most once every 12 hours each. A reminder issues a new link and the earlier one stops working.
- **Sharing a link by hand:** **Guests → People** offers **Share attendance link** in a confirmed, non-crew guest's menu (same owner/admin rule; hidden after the start and for a cancelled event) for organisers who reach guests by text or chat. It sends no email. Only the link's digest is stored, so each use issues a new link under the event row lock and shows it once with **Copy link**: a guest not yet asked is asked now (a later send skips them and they show *No reply*), and for a guest already asked the new link replaces the emailed one, which stops working (a queued email with it is dropped at delivery). A guest who already answered keeps their answer and can change it with the new link. Shared links set `sentAt`, so the 12-hour reminder clock starts again. Audited `ATTENDANCE_CHECK_LINK_SHARED` with the registration id and whether a link was replaced (never the token), and limited to 60 per 10 minutes (`attendanceCheckLink`). The Emails card's "last sent" line counts emails only.
- **The email:** subject "Are you still coming to {event}?" (reminders start with "Reminder:"), with the event's date and time in its own timezone, the location, and two large buttons (**Yes, I'll be there** / **No, I can't make it**) that open the guest's private form with that answer preselected. Links use the absolute `NEXT_PUBLIC_BASE_URL`. A queued email is dropped at delivery if its link was replaced, the guest has already answered, is no longer confirmed or was removed, or the event was cancelled, and it expires when the event starts.
- **The guest's form** (`/attend/:token`): the event summary, the guest's own name and email (read-only), Yes or No, and an optional note of up to 500 characters. The guest can change their answer until the event starts. After the start, after a cancellation, or when the registration is no longer confirmed, the page shows a friendly closed message. A link that is unknown or has been replaced is a real 404.
- **"Free the place when a guest says No"** (off by default): when it is on, a No cancels the registration through the same self-cancel path as the ticket page, so capacity, waitlist promotion and team rules (leader handover, team units) apply exactly as usual, and the guest sees "Your place has been released". A released place cannot be taken back from the form, and the guest must register again. A guest who is already checked in keeps their place, and their answer is still recorded. When the switch is off, a No is only recorded. The email follows the switch at delivery: only when it is on does it say that answering No gives up the place (it never promises the waitlist, because approval-only events do not promote anyone).
- **What organisers see:** the card shows "Not sent yet" or how many guests were asked, when and by whom the last email was sent (in the event's timezone), the numbers coming, not coming and with no reply, how many are newly confirmed and not yet asked, and how many places were released. **Guests → People** shows a badge per guest (*Coming*, *Not coming*, *No reply*, *Not asked*) and the guest's note, and has a server-side **Attendance confirmation** filter with counts that saved views and links keep (`attendance=`). The attendee CSV gains **Attendance confirmation** and **Attendance note** columns (formula-safe). The check-in desk shows the badge, and the Overview readiness card shows a counts-only line ("Attendance: 12 coming · 3 not coming · 5 no reply") to organisation owners and admins once anyone was asked.
- **Audit and limits:** sends, reminders, setting changes, shared links and released places are audited (`ATTENDANCE_CHECK_SENT`, `ATTENDANCE_CHECK_REMINDED`, `ATTENDANCE_CHECK_SETTINGS_UPDATED`, `ATTENDANCE_CHECK_LINK_SHARED`, `ATTENDANCE_CHECK_RELEASED`) without tokens. Sends and reminders share a limit of 10 per hour, and replies are limited per link and per address.
- **Data:** answers are deleted with their registration or event. Cloning an event copies the release setting but never the questions or answers. The personal data export includes your own answers (when you were asked, your reply, when you replied, and your note).

## Team registration

One-off events can register people in teams (hackathons, game jams, competitions). The design contract, including every rule below, is [Team registration](TEAMS.md).

- Organisers turn it on in the event's **Publishing** section: registration mode (individual or team), minimum and maximum team size, and whether people may register solo (*Teams only*, *Solo allowed*, or *Solo with matching*). Recurring series stay individual. The mode cannot change once the event has registrations, and the maximum cannot drop below the largest team.
- In team mode, capacity counts **units**: each team and each solo registrant is one unit, so a team never takes more than one spot. Every unit count happens under the same event lock as other capacity changes, so concurrent team creation never oversells.
- The registration form offers **Create a team** (name unique per event, ignoring case), **Join with a link**, and, when allowed, **Register solo**. New members take the team's status and never change capacity; a full or rejected team cannot be joined.
- The leader gets a private team page link by email (`/team/:token`, stored only as a hash) and, when signed in, reaches it from **Account → Registrations**. There they rename the team, share or regenerate the join link (`/:orgSlug/:eventSlug/team/:joinToken`, which shows only the team name and size and follows the event's visibility and invite rules), add a member by name and email (the member is emailed their own ticket), remove members, hand over leadership, mark the team as *Looking for members*, and disband it.
- Members see their team name, leader and teammates on their ticket and can leave the team, which cancels their registration. If the leader cancels, leadership passes to the longest-standing member and a fresh team page link is emailed to them; when the last member leaves, the team is deleted and its unit freed.
- With *Solo with matching*, solo registrants can list themselves as looking for a team with a short headline and up to eight skills. Leaders of teams with space and other listed seekers of the same event see first name and last initial, headline and skills only (never email, answers, or ticket links). Leaders invite seekers and seekers ask to join teams that are looking; accepting moves the registration into the team and frees the solo unit.
- Organisers approve, reject and promote **whole teams** from the Guests tab's Teams view; an individual action on a team member is refused. Teams below the minimum size are marked *Incomplete* and cannot be approved. Organisers can also rename teams, move a member to another team, and delete a team with undo. A freed unit promotes the oldest waitlisted unit (team or solo) unless the event needs approval.
- Each member gets the usual status emails, naming the team. The attendee CSV, check-in desk, badges (`{{team}}`), personal data export and post-event report include team details.
- Every team and guest list is paged on the server, so events with hundreds of teams and thousands of registrations stay fast: the organiser Teams and People views and the check-in desk load in steps with **Load more**, the Move to team picker and the team and ticket pages' matching lists in steps of 20 with search, Invites in numbered pages, and **Export emails** downloads every guest matching the current filters. Guests · People, Guests · Teams, Judging → Submissions and Judging → Results each have **Export CSV** for exactly the filters and search showing, streamed from the server in bounded batches. Feedback responses page on the server, 25 at a time.
- In the mobile API, organisers list teams and approve, reject or promote whole teams, attendees see their own team, and guest and check-in rows carry the team name. Creating, joining and managing teams stays on the website: `POST /api/mobile/v1/rsvp` registers solo where allowed and returns `TEAM_REQUIRED` on a teams-only event. The machine API has no team fields.

## Event crew

One-off events can list their organising team. The design contract is [Event crew](CREW.md).

- Organisers add, edit, reorder, show or hide, and remove crew members (name, email, food preference, role, bio, photo, LinkedIn) in **Guests → Crew**, which also groups food preferences for catering.
- Every crew member gets a confirmed ticket by email ("You're on the crew"), with a **Crew** chip on the ticket page and at the check-in desk. Crew count as going but never against the event's capacity. Adding someone who already registered solo turns their registration into the crew ticket and frees their place.
- A crew sign-up link (`/crew/:token`) lets crew add themselves; they start hidden from the event page until an organiser reviews them. Organisers can create, rotate, and disable the link.
- An optional **Crew** section on the event page (off by default, in **Event page → Sections**) shows visible members' cards, never emails or food preferences.
- Crew tickets cannot be cancelled by their holder or edited and removed from Guests · People, and crew never join teams.
- Crew are never asked to confirm attendance and never enter hackathon projects. The mobile and machine APIs show crew tickets as ordinary confirmed registrations (the mobile `capacityUsed` still leaves them out); crew management is web-only.

## Hackathon submissions, judging, and results

One-off events in either registration mode can take project submissions, have them judged against a rubric, and publish results. The design contract is [Hackathon submissions, judging, and results](HACKATHON.md); it builds on [team registration](TEAMS.md).

- Organisers (owners and admins) turn submissions on from the event dashboard's **Settings** tab; the **Judging** tab (`?tab=judging`) then appears and holds the rest: submissions on or off, the submission window (shown in the event timezone and checked against server time whenever an entrant saves), whether **all judges see all submissions** or only the ones assigned to them, and whether the **project gallery** becomes public once the window closes. Submissions can't be turned off once judging has started or results are published (that would hide results, the gallery, and the judging workspace); moving the closing time stops new projects. Settings changes are audited.
- An **entrant** is a team (on team events) or a single registration (a solo registrant, or anyone on an individual event). Only confirmed entrants can submit. A project has a title (up to 120 characters), a plain-text summary (up to 4000), and optional `https:` links to the code, a demo, and a video (up to 500 characters each). Entrants save a draft, submit, edit while the window is open, and withdraw; a disbanded team or cancelled registration takes its project with it, while an organiser's undo of a deleted team or registration brings back its project and judging record. A solo registrant who joins a team (or is moved into one) can't bring a solo project along: a submitted one must be withdrawn first (an organiser can also disqualify it), and a draft or withdrawn one is discarded. Whoever submits gets a *submission received* email.
- Teams edit their project from the team page (`/team/:token`) or, signed in, from **Account → Registrations** (any member, `/account/submissions/:eventId`). Signed-in solo registrants use the same account page; otherwise they ask for a private **submission link** on their ticket page. The link (`/submit/:token`) is emailed only to the registration's own address, stored as a hash, and replaced (retiring the old one) when requested again, at most once a minute. Holding the ticket QR alone never opens a submission.
- **Judges** are organisation owners and admins, or event co-organisers invited with the **Judge** permission. A co-organiser who is only a judge sees just the judging workspace on the event dashboard: no guests, answers, emails, check-in, page editing, or settings, and the event does not appear in their mobile organiser app. Judges see project content (title, summary, links, team or entrant name), never entrant emails, answers, or ticket links. A judge whose own account is registered on an entry never sees it and cannot score it, and organisers cannot assign it to them.
- The **rubric** holds up to 20 criteria, each with a name, description, weight (1 to 10), and maximum score (1 to 10), and can be changed only before judging starts. While judging is **Open**, judges save scores as they go (whole numbers from 0 to the maximum) and submit their review, with an optional private comment for organisers, once every criterion is scored. **Closing** judging freezes all scores; it cannot reopen while results are published.
- A project's **result score** is the average, over judges who submitted a review and can still judge the event without a conflict of interest on that entry, of `Σ(weight × score / maxScore) / Σ weight × 100`, rounded to one decimal; projects without a submitted review have no score, and tied scores share a rank (1, 1, 3). **Adjust for harsh/generous judges** (owners and admins, audited) ranks by an adjusted score instead: each judge's scores are rescaled around their own average (50, with 15 points per standard deviation; judges with fewer than 3 reviews or identical scores stay raw). The table and CSV always show both scores. Organisers see the ranked table with per-criterion averages, each judge's progress, and every review with its comment, and can download the scores as CSV (owners and admins only; judge names but no emails or comments; audited).
- Organisers disqualify a submitted project with a private reason (the entrant never sees it) and can reinstate it. Both are audited, and a disqualified or withdrawn project loses any award.
- **Awards** (for example *Overall winner* or *Best design*) have places 1, 2, 3 and so on, filled by hand from the ranked table; only submitted projects can win. **Publishing results**, once judging is closed, shows `/:orgSlug/:eventSlug/results` with each award, the winning project titles, team or entrant names, and links, and, if the organiser turned on **Email entrants when results are published**, emails each confirmed registration once. Scores and judge comments are never public. Unpublishing hides the page again and cancels announcements not yet sent; publishing again emails only those whose announcement was cancelled, never anyone twice. Both are audited.
- **Hackathon emails** (Judging → Setup) are opt-in and **off by default** on every event: *Email entrants when results are published* and *Email a receipt when a project is submitted*. With the first off, publishing results emails nobody; turning it on later offers **Send results email now** on the Results tab (once, with the recipient count and a note about mail-provider sending limits). The publish confirmation says which will happen. Registration, team, submission-link, verification, password-reset, invitation, broadcast and attendance emails always go out and have no switch. Cloning an event copies both switches.
- **Assign judges automatically** (Judging → Progress, owners and admins): pick the judges per project (default: the event's target, else 3), keep or replace current assignments, and who judges (invited judges by default; owners and admins only when ticked). Every submitted project gets that many judges, never one registered on it, with the load spread evenly and the same result on every re-run. A preview shows each judge's assignments before and after and the projects that can't reach the number; applying re-checks that nothing changed, switches judges to their assigned projects only, stores the target, and is audited.
- **Judging progress** (Judging → Progress, owners and admins): projects below the target number of submitted reviews, each judge's assigned, started and submitted reviews with a completion percentage, outlier scores (a judge more than two standard deviations from the other judges on a project, or two judges more than 25 points apart), and reviews with saved scores left unsubmitted for over 24 hours, each as numbered pages of 25.
- Judges can press **Score next project**: the server opens a project they started, else the one with the fewest reviews (oldest first), and after each submitted review the next one opens on its own until a "You're all caught up" state.
- Judging lists are paged on the server: judges score from a list of 25 at a time with **To score**, **In progress** and **Reviewed** filters and search; organisers page Submissions (50 at a time, with status filter and search) and Results (numbered pages of 50, with ranks always computed over every project); the public project gallery shows 24 projects per page with search (project title, team or entrant name), an **Award winners** filter and **Newest** / **A–Z** / **Awards first** orders (the filter and awards order once results are published), award badges on winning projects, and shareable URLs that work without JavaScript; the results page gains the same search once it lists more than 10 winners.
- The results page, the project gallery (`/:orgSlug/:eventSlug/projects`), and submission pages follow exactly the event page's visibility, publication, and invite rules, and are a real 404 otherwise.
- The personal data export includes the projects of the user's registrations, without scores, comments, or disqualification reasons.
- The mobile API offers the judge's scoring workspace (the project list with filters and search, **Score next project**, the rubric, saving scores and submitting a review) under the same visibility and conflict-of-interest rules; entrant submissions, judging management and results stay on the website. The machine API does not expose submissions, judging or results.

## Saved views

The event dashboard's long lists (Guests → People and Teams, Judging → Submissions, Results and Progress) keep their filters and search in the address bar, so a reload, a bookmark or a pasted link reopens the same view (`?tab=guests&sub=people&status=waitlist&q=…`). Each list accepts only its own allow-listed keys (`status`, `kind`, `team`, `attendance`, `q`, `scored`, `show`); unknown keys and values are dropped, and switching tab or sub-tab clears them.

- A **Views** menu on each list applies built-in presets: People *Waitlisted*, *Checked in*, *Not checked in* (going and not yet at the door) and, on team events, *Solo*; Teams *Incomplete*, *Pending approval* and *Looking for members*; Submissions *Not submitted* (confirmed teams and solo registrants whose project isn't submitted: none yet, a draft, withdrawn or disqualified), *Drafts* and *Disqualified*; Results *Unscored* and *Scored by fewer than 2 judges* (ranks unchanged); Progress *Below target*. Every preset is a filter the server computes, with its own count (new chips: People *Not checked in*, Teams *Looking for members*, Submissions *Not submitted*, Results *Unscored* / *Fewer than 2 judges*, Progress list chips).
- **Save current view…** stores the current filters under a name (up to 60 characters), optionally **shared with the team**: everyone who can open that list on that event sees it under *Shared views*. Your own views can be renamed, shared or unshared, and deleted from **Manage views…**; owners and admins can also delete views others shared. Each person keeps up to 50 views per list; a menu shows up to 100, always listing your own views first and filling the rest with the oldest shared ones, and each list reads its views on its own. **Copy link** copies a link to the list with the current filters.
- A view never gives access: it only picks filters inside a list, and every list re-checks its own permission on the server (People and Teams: owners/admins or `MANAGE_REGISTRATIONS`; Judging: owners/admins). Views are stored in `SavedView`, scoped to their event, organisation and list, re-validated against the list's allow-list when saved and when read, and deleted with their event, organisation or creator. Creating, deleting and sharing (or unsharing) a view is audited (`SAVED_VIEW_CREATED`, `SAVED_VIEW_DELETED`, `SAVED_VIEW_SHARED`, `SAVED_VIEW_UNSHARED`, with the list only, never the name or filters); the actions use the `action` rate-limit bucket.

## Tickets and check-in

- Opaque ticket/check-in tokens with QR and manual entry flows.
- Printable/downloadable attendee ticket. For in-person events with a valid http(s) map link, the venue on the ticket opens the map in a new tab.
- Live ticket: when the attendee is checked in (scan, manual, offline replay, station, or the mobile app), an open ticket page tears off its QR stub and shows the check-in time, without a reload. Reloading a checked-in ticket shows the torn state and no QR.
- Organiser attendee lookup, direct check-in, and check-in undo.
- In-venue attendee badge printing after a QR, manual, or lookup check-in. With badge printing on, each check-in opens a quick print sheet showing that attendee's real badge with one Print button (Enter prints), Skip, and Edit design. The badge designer offers three high-contrast templates (Classic, Bold, Minimal), with the name always the largest text; badge-stock presets (A6, 4 × 6 in, 3 × 4 in, 4 × 3 in, CR80 ID card) in portrait or landscape plus custom sizes, with layouts and type that scale to the stock; card text with optional label and footer; email and organisation logo toggles; registration answers chosen from the sign-up form, reordered, and relabelled; long names that shrink to stay on one line; drag, arrow-key nudging and a properties panel for each item; undo/redo; previews with short and long sample names; a test-card print with sample data; and export/import of the design file to set up another desk. Every card includes the attendee's scannable check-in QR, generated locally. Designs are kept in the browser per event.
- A PIN-locked venue check-in station at `/:orgSlug/:eventSlug/check-in` for door volunteers without a Yuyu account (`lib/checkInStation.ts`, `lib/stationPin.ts`); organisers set and reveal the PIN from the Check-in tab.
- Offline roster storage in the browser and later synchronization.
- Immutable check-in event history for online and offline actions.
- Custom check-in lists per event beyond venue entry, such as "Swag collection", "Lunch – Day 1" or "Workshop B". The check-in page has a list switcher (**Entry**, which is the unchanged door desk, plus each open list, at `?list=<id>`). With a list selected, a scan, a typed ticket code or a search result marks the guest for that list at once, with success, "Already checked in to Swag at 10:42" and refusal feedback (sound and vibration like the entry desk, announced politely to screen readers), **Undo**, collected / eligible counts, a waitlist **Override** with the same rule as entry, and a guest view filtered by collected or not collected. Eligibility is the entry gate (`gateCheckInForStatus`): confirmed guests pass, the waitlist needs Override, pending and declined registrations are blocked; a list can also require entry check-in first. **Manage lists** (Check-in tab and check-in page) creates, renames, reorders, archives and restores lists and toggles the entry requirement; archived lists are read-only, hidden from the desk, and keep their data. List check-ins never change entry check-in, `RSVP.checkedInAt`, the live ticket or the entry history. Each guest's lists show in the Guests list, and the attendee CSV gains a `Check-in: <list>` column per list with the time or blank. Standalone events only; series occurrences, the mobile API, offline list check-in, the venue station and live ticket updates for lists are not covered yet.

Only eligible confirmed attendees receive a scannable ticket by default. Organisers can explicitly handle exceptional status cases where supported by the check-in workflow.

## Feedback and certificates

- Per-event feedback form with configurable title, thank-you message, open/closed state, and custom questions. Organisers can start from quick pulse, event review, or session-and-speaker-review templates, then tailor the form before opening it.
- When certificates are disabled, feedback is anonymous: no email or RSVP identity is collected, and repeat responses are allowed.
- When certificates are enabled, the submitted email must match a confirmed RSVP. Repeat submissions from the same email are allowed.
- Successful eligible submissions can download a generated JPEG certificate using an opaque token.
- Certificate designer: upload JPEG/PNG/WebP artwork (up to 5 MB), then build the certificate from up to 20 layers. Text layers take fixed text plus merge tags ({{name}}, {{event}}, {{eventDate}}, {{organisation}}, {{issueDate}}; dates use the event's timezone) with font, size, colour, bold, italic, uppercase, letter spacing, alignment and line breaks; long text shrinks to fit its box. Image layers hold logos, signatures or seals (JPEG/PNG/WebP up to 5 MB, transparency kept), fitted inside their box. Layers can be selected, reordered, duplicated and deleted, dragged with centre snapping, resized, nudged with arrow keys, or placed with numeric controls. An exact server-generated preview checks fonts and fitting before saving feedback settings. Templates saved in the earlier single name-area format are upgraded automatically.
- Certificate layouts are snapshotted when feedback is submitted; subsequent layout edits affect new submissions only. Without custom artwork, the standard certificate is used.
- Feedback links are shared manually; opening a form does not automatically email attendees.
- Organisation owners and admins can download feedback responses as CSV (`/api/exports/events/:eventId/feedback`); owners, admins, and collaborators with `MANAGE_REGISTRATIONS` can download the attendee list as CSV.

## Event analytics

- The event dashboard's analytics include a registration funnel. Each step has a plain-language hint, a bar sized as a share of everyone who responded, and a percentage of the previous step, never over 100%.
- After an event or occurrence ends, owners and admins can download a post-event PDF report (sign-up timeline, arrivals by time and device, programme, speakers and sponsors, answer counts, emails sent, and team). Typed answers, emails, and phone numbers are counted, never copied into the report.

## Administration and operations

- Instance-wide super-admin area restricted by `SUPER_ADMIN_EMAIL`, with its own top bar instead of the dashboard sidebar. Every super-admin page checks super-admin access and the MFA step-up itself.
- Super-admin control to disable new password and Google account creation while preserving existing-user sign-in.
- Super-admin instance settings for SMTP delivery, Google SSO, and display-only backup posture; instance-managed service secrets are encrypted at rest and never displayed after saving. Saved settings are read from the database on every send and sign-in, so they apply on every replica without a restart; saved SMTP replaces the `SMTP_*` environment values as a whole. **Send test email** checks delivery after saving, and **Retry failed email (last 7 days)** requeues only recent failures.
- An optional operational alerts webhook (Mattermost or Slack-compatible) for uncaught server errors, server error logs, sign-in failures, email delivery failures, browser crashes (`POST /api/client-errors`), and process starts. Alert text is redacted, de-duplicated, and rate capped; the webhook URL is write-only and encrypted. See [Production operations](production-operations.md#operational-alerts-webhook).
- `node scripts/check-instance-secrets.mjs` confirms that `MFA_ENCRYPTION_KEY` can decrypt the secrets saved in the panel, without printing them.
- Read-only super-admin insights: 30-day activity and growth (signups, organisations, events, registrations, check-ins, feedback, broadcasts), email outbox health by message kind and recent broadcasts (subject and audience only), security posture (MFA adoption, owners/admins without MFA, unverified accounts, sign-in methods, sensitive audit actions, machine API clients with credential lifecycle but never secrets), storage breakdowns, and per-user and per-organisation support pages. Tokens, password and credential hashes, registration answers, storage keys, and message bodies are never shown.
- Separate TOTP step-up verification for super-admin access; verification lasts 10 minutes and requires an enrolled authenticator.
- Organisation, user, event, invitation, authentication, monitoring, operations, storage, and searchable audit-log views.
- Public liveness and secret-protected database readiness endpoints.
- Outbox delivery, retries, retention cleanup, scheduler-heartbeat monitoring, and safe failed-email diagnostics.
- Private S3-compatible object storage with database asset accounting.
- Application audit events plus database-triggered fallback audit records for important mutations.
- Owner-managed, tenant-bound machine API clients with explicit scopes, one-time credentials, expiry, rotation, revocation, and disablement.
- Versioned machine endpoints for standalone event metadata and minimal confirmed-participant rosters, including attendance filtering and separately scoped check-in timestamps.
